## 模块划分

### 布局生成

1. 参数生成模块
2. 自由绘制模块
3. **Contour extraction**-轮廓提取模块

三个模块采取统一的svg+canvas画布混合模式：canvas负责画笔工具，性能高，本质是像素点操作；svg适合保证缩放不失真，每一个元素独立监听`<path>`，可使用浏览器原生的命中检测，使用canvas需要自己手动实现。因此计划将后者作为前者的遮罩层。

痛点是轮廓提取部分的左右分栏布局，并且需要切换到重叠模式，有点统一布局架构的压力。

#### 缩略图生成模块

不渲染来生成场景截图的gl库的原理：传统WebGL上下文绑定到浏览器的可视化窗口即Canvas元素，GPU渲染结果显示到屏幕中。

Headless-gl不创建可见窗口，内存中创建Web GL上下文窗口，GPU渲染结果写入离屏缓冲区，使用离屏渲染，通过库接口从GPU内存之中读取像素数据，然后利用sharp将像素数据编码为图片文件。

后者支持GPU或者CPU渲染，前者快后者慢，但是适合服务器没有显卡的环境。

```javascript
// 传统方式：绑定到 Canvas 元素
const canvas = document.getElementById('canvas');
const gl = canvas.getContext('webgl');

// Headless-gl：直接创建上下文
const { WebGLRenderingContext } = require('gl');
const gl = new WebGLRenderingContext(320, 320);
```

该库是利用ANGLE库在后台调用电脑图形驱动在内存中构建虚拟GPU环境供WebGL指令运行：系统主内存上放置运行所需核心库、js脚本、缓冲几何数据、纹理数据等等；显存用于存储渲染缓冲区、纹理、着色器程序等实际参与GPU计算的资源。WebGL上下文本身是在内存中，但它关联的是绘图缓冲区和纹理等核心资源在显存中。

##### 方案一

Headless-gl，这是一个nodejs原生模块，内存中创建上下文，不依赖窗口系统，无需浏览器环境，但是不太理想，这个库需要额外的cpp库的编译支持，不是纯正的ts实现，不太优雅，需要自己搞定编译和环境问题。

##### 方案二

electron 离屏渲染，官方api，和现有代码集成简单，官方支持，就是需要完整渲染进程，内存占用相对较高

区别于隐藏窗口，其不需要创建一个普通的 `BrowserWindow`然后设置 `show: false`本质上依旧是走了完整的渲染管线，有完整窗口只是不可见，依旧是在显示器表面分配了空间的，获取数据通过捕捉页面capturePage或者截图。

后者直接没有窗口句柄，创建 `BrowserWindow` 时启用 `offscreen: true`，不分配表面，直接内存中分配帧，获取数据直接借助paint事件获取位图数据，开销更低，速度更快。

##### 方案三

`@rendergl/headless-three-webgpu` Nodejs直接创建webGPU上下文，无需浏览器和窗口，是云端3D渲染平台 **[render.gl](https://render.gl/)** 核心渲染层的一部分，周下载量只有几十个，并不主流。

最终抉择，方案二，简单可靠，并且长期维护。

##### 存疑

绘制模式和轮廓编辑的回退控制是否应该独立控制，两种模式是互斥的，状态控制应该也是互斥的，切换到轮廓编辑模式的时候，绘制模式的数据进行清理，因为绘制模式结束后，轮廓编辑操作会叠加其上，算了还是二者都做一次：统一管理的情况下，就是绘制轮廓作为新建轮廓操作被记录，和删除轮廓、点和拖拽、增加点公用一个操作队列，因为不同绘制方式都是实时生成的操作，不是统一编辑的，因为统一进行操作这是一种轮廓提取部分的底图操作而不是轮廓画布的操作。
